EXECUTIVE SUMMARY 
 
Diabetic retinopathy (DR) can cause irreversible vision loss if it is not detected early, 
and training deep learning models for its detection normally requires centralising 
sensitive retinal images. This project presents EdgeRetina, a research prototype fo r 
privacy-aware DR classification using simulated federated learning and explainable 
deep learning. The system classifies fundus images from the APTOS 2019 dataset 
(3,662 images) into five severity grades using MobileNetV3Small and 
EfficientNetB0. On a held-out test set, EfficientNetB0 achieved 71.1% accuracy with 
40.9% macro -F1, and MobileNetV3Small achieved 63.3% accuracy with 42.0% 
macro-F1; the low macro -F1 reflects class imbalance. A simulated federated 
workflow with four clients applies L2 -norm update  clipping and Gaussian noise 
before Federated Averaging; this is privacy -inspired processing and not a formally 
verified differential privacy guarantee. Grad -CAM heatmaps provide visual 
explanations. A Flask web application supports image upload, predictio n with 
confidence and class probabilities, Grad -CAM display, training and a SQLite 
prediction history. The report documents the design, implementation, results and 
limitations of the work.

CHAPTER 1 
INTRODUCTION 
Diabetic retinopathy (DR) is one of the most common microvascular complications of 
diabetes mellitus. It develops when prolonged high blood sugar damages the small 
blood vessels that nourish the retina, the light-sensitive tissue at the back of the eye. In 
its early stages the disease is usually silent: a patient may notice no change in vision 
while microscopic lesions are already forming. If the condition is not detected and 
managed in time, it can progress to macular oedema, retinal haemorrhage, and 
eventually irreversible vision loss. Regular screening of retinal fundus photographs is 
therefore a cornerstone of diabetes care, because early detection allows timely referral 
and treatment. 
Artificial Intelligence (AI), and deep learning in particular, has changed how 
medical images are analysed. Convolutional neural networks (CNNs) learn visual 
patterns directly from labelled images and can grade retinal photographs without hand-
crafted feat ures. Landmark studies have shown that such models can approach the 
performance of trained graders (Gulshan et al., 2016; Ting et al., 2017; Gargeya & 
Leng, 2017). Yet moving these models from research into real healthcare settings raises 
problems that go beyond accuracy: the training data are sensitive, they are scattered 
across institutions, and the predictions of a deep network are difficult for a clinician to 
inspect. 
This project, EdgeRetina, addresses three of these concerns together. It 
classifies retinal fundus images into five diabetic retinopathy severity categories, it 
demonstrates a simulated federated learning workflow in which training data stay in 
separate client partitions, and it produces Grad -CAM visual explanations so that a 
prediction can be examined and not merely accepted. The whole system is delivered as 
a Flask-based web application with prediction history stored in SQLite. The work is an 
academic research prototype develope d for the course SWE3004 – Software Design 
and Development Project of the M.Tech Software Engineering programme. 
1.1 Objective 
The primary objective of this project is to design, implement and evaluate a software 
system that classifies diabetic retinopathy severity from retinal fundus images, while 
demonstrating privacy -aware distributed training and explainable predictions. The

specific objectives are listed below. 
• To develop a deep learning based system for five -class diabetic retinopathy 
classification (No DR, Mild, Moderate, Severe and Proliferative DR). 
• To use the APTOS 2019 Blindness Detection dataset and to validate and 
preprocess the retinal images before training. 
• To implement and compare two lightweight transfer -learning architectures, 
MobileNetV3Small and EfficientNetB0. 
• To simulate four hospital clients and train a shared model with Federated

• To apply L2-norm update clipping and Gaussian noise to client model updates

• To evaluate the models with accuracy, precision, recall, F1-score, macro-F1 and

• To generate Grad-CAM heatmaps that show which image regions influenced a 
prediction. 
• To deliver the system through a Flask web interface that supports image upload, 
prediction with confidence and class probabilities, training control and 
prediction history in SQLite. 
 
1.2 Motivation 
Three practical observations motivate the project. The first is the scale of the screening 
problem. Diabetes is common and DR screening must be repeated at regular intervals, 
so the number of fundus photographs to be reviewed is very large. Manual grading is 
slow and depends on scarce specialist time. An automated first-pass classifier can help 
prioritise images for expert review, which is the role EdgeRetina is meant to 
demonstrate. 
The second observation is the problem of data governance. Retinal images are 
medical records. Conventional centralised training requires copying images from every 
contributing hospital to one server, which creates privacy, security and legal 
difficulties. Federated learning (McMahan et al., 2017) offers a different arrangement 
in which each participant trains on its own data and only model parameters or updates 
--- PAGE 15 ---
3 
 
travel to a coordinating server. Reviews of the field describe this as a promising route 
for collaborative medical AI (Rieke et al., 2020; Sheller et al., 2020). However, 
federated learning alone is not a privacy guarantee, because shared updates can still  
leak information about the training data (Zhu et al., 2019). This motivates adding 
update-level protections such as clipping and noise, and being honest about what those 
protections do and do not provide. 
The third observation concerns trust. A bare class label from a neural network 
is hard to accept in a clinical context. Visual explanation methods such as Grad -CAM 
(Selvaraju et al., 2017) give a reviewer something to look at, even though they are not 
a proof of correctness. Combining classification, simulated federated training, privacy-
inspired update processing and explanation in one working application is the motivation 
for EdgeRetina. 
1.3 Background 
1.3.1 Diabetic Retinopathy and Its Severity Grades 
The international clinical classification of diabetic retinopathy grades the disease from 
no apparent retinopathy to proliferative retinopathy (Wilkinson et al., 2003). The 
APTOS 2019 dataset used in this project follows a five-level labelling of the same idea. 
In No DR, no abnormality is visible. In Mild DR, only a few microaneurysms are 
present. Moderate DR shows more extensive microaneurysms, haemorrhages and 
exudates. Severe DR indicates widespread haemorrhages and vascular changes that 
place the eye at  high risk of progression. Proliferative DR is the advanced stage, in 
which abnormal new vessels grow on the retina and can bleed or cause retinal 
detachment. The labels are ordered, so confusing Mild with Moderate is a smaller error 
than confusing No DR with Proliferative DR; this ordinal nature is reflected later in the 
evaluation by the quadratic weighted kappa and the mean absolute grade error. 
1.3.2 Deep Learning and Transfer Learning 
Training a deep CNN from scratch needs a large number of labelled images. Medical 
datasets are usually much smaller. Transfer learning reuses a network that was first 
trained on a large general image collection and adapts it to the new task (Yosinski et 
al., 2014). Typically the pretrained feature extractor is kept and a new classification 
head with five outputs is trained first; some of the deeper layers are then unfrozen and 
fine-tuned at a low learning rate. EdgeRetina follows this idea with two compact 
--- PAGE 16 ---
4 
 
architectures, MobileNetV3Small (Howard et al., 2019) and EfficientNetB0 (Tan & Le, 
2019), both of which are efficient enough to be trained and served on an ordinary 
workstation. 
1.3.3 Federated Learning and Privacy-Inspired Update Processing 
In federated learning a server sends the current global model to several clients, each 
client trains it on local data, and the server combines the results into an improved global 
model. The standard combination rule is Federated Averaging (FedAvg), in which each 
client's contribution is weighted by its number of training samples. Because the shared 
quantity is a model update rather than an image, the raw data never leave the client. 
Updates can nevertheless be inspected or inverted by a curious server, so a  common 
precaution is to bound the size of every update by clipping its L2 norm and then to add 
random Gaussian noise (Abadi et al., 2016; Geyer et al., 2017). When this is combined 
with a formal privacy accountant it yields a differential privacy guarante e (Dwork & 
Roth, 2014). EdgeRetina implements the clipping and noise steps but does not 
implement a privacy accountant, so the project describes them as privacy -inspired 
processing and makes no formal (ε, δ) claim. 
1.3.4 Explainable Deep Learning 
Gradient-weighted Class Activation Mapping (Grad-CAM) produces a coarse heatmap 
showing which regions of an input image contributed most to the score of a chosen 
class. For a retinal image the heatmap may highlight the optic disc, the macula or areas 
with exudates. It is a visual aid for inspection. It is not a lesion segmentation and it does 
not establish that the model is clinically right (Adebayo et al., 2018). The project treats 
it accordingly. 
1.4 Problem Statement 
Diabetic retinopathy classification from fundus images presents several linked 
challenges. Manual examination is time consuming when many images must be 
reviewed. The APTOS 2019 dataset is imbalanced, with 1,805 No DR images against 
only 193 Severe DR imag es, so a model can achieve a respectable accuracy while 
performing poorly on the rarer and clinically more important classes. Variations in 
brightness, focus and contrast between images further affect predictions. Finally, 
collecting images from several ho spitals into one place conflicts with privacy 
requirements, and the models that result are usually opaque.

5 
 
The problem addressed by EdgeRetina is therefore to build a system that 
supports five-class DR classification, explains individual predictions, and demonstrates 
distributed training with privacy -inspired update processing, all within a reliable 
model-management and evaluation workflow that a user can operate through a web 
interface. 
1.5 Scope of the Project 
EdgeRetina is a research prototype for privacy -aware diabetic retinopathy 
classification. The scope covers retinal image validation, preprocessing, model training, 
model evaluation, simulated federated learning, privacy -related update processing, 
prediction with confidence estimation, Grad -CAM explanation and prediction -history 
storage. The boundaries of the work are stated explicitly so that the results are not over-
interpreted. 
• The four federated clients are software simulations created from partitions of 
one dataset. They are not real hospitals and the project does not demonstrate 
deployment across institutions. 
• Clipping and Gaussian noise are privacy -inspired operations. No privacy 
accountant is implemented and no formally verified differential privacy 
guarantee is claimed. Homomorphic encryption and secure aggregation are not 
implemented. 
• The reported test accuracy and macro -F1 values belong to the centralised 
evaluation of the two architectures. They must not be read as the accuracy of 
the federated global model. 
• Grad-CAM heatmaps support visual inspection. They are not lesion 
segmentations and they do not replace clinical assessment. 
• The system is meant for academic and research use and is not a medical device 
or a substitute for an ophthalmologist. 
 
1.6 Proposed Approach and Main Contributions 
The proposed system validates the APTOS 2019 images, preprocesses them by 
resizing, contrast enhancement and normalisation, and divides them into training, 
validation and test sets. Two architectures are trained and compared on the five -class 
task. For the federated experiment the training data are divided among four simulated 
--- PAGE 18 ---
6 
 
clients. Each client trains locally, its model update is clipped and perturbed with 
Gaussian noise, and the server aggregates the processed updates with FedAvg to form 
a global model that can be redistributed for further rounds. A prediction module returns 
the predicted class, its confidence and the full class-probability distribution, and a Grad-
CAM module overlays a heatmap on the image. 
The main contributions of the project are summarised as follows. 
• An end-to-end working prototype that integrates five -class DR classification, 
simulated federated learning, privacy -inspired update processing and Grad -
CAM in a single Flask application. 
• A measured comparison of MobileNetV3Small (63.3% test accuracy, 42.0% 
macro-F1) and EfficientNetB0 (71.1% test accuracy, 40.9% macro -F1) on a 
common test set, with a confusion-matrix based analysis of per-class behaviour 
under class imbalance. 
• A modular software design in which dataset validation, preprocessing, training, 
prediction, federated components, explanation and persistence are separate 
services. 
• A transparent statement of limitations, including the absence of a formal privacy 
guarantee and of federated evaluation results, which keeps the claims of the 
work accurate.

CHAPTER 2 
PROJECT DESCRIPTION, LITERATURE SURVEY AND GOALS 
2.1 Project Description 
EdgeRetina is a web -based research workspace for five -class diabetic retinopathy 
classification. A user opens the application in a browser, uploads a retinal fundus image 
and receives the predicted severity grade together with a confidence value and the 
probability assigned to every class. A Grad -CAM overlay can be generated for the 
prediction, and each prediction is saved with a timestamp so that it can be reviewed 
later in a history page. A researcher uses the same interface to validate the dataset, run 
centralised model training for MobileNetV3Small and EfficientNetB0, and run the 
simulated federated training with privacy-inspired update processing. 
Behind the interface the backend is divided into services for image validation 
and preprocessing, model loading, training, prediction, evaluation, Grad -CAM 
generation and database access. The federated component contains a client that 
performs local traini ng and generates an update, a privacy processor that clips the 
update and adds Gaussian noise, a server that receives the processed updates, and an 
aggregator that combines them with FedAvg. The interface is intentionally candid about 
the status of each result: it shows the best verified model and its measured test accuracy, 
labels low-confidence predictions as uncertain, and describes the privacy component as 
experimental.

2.3.1 Deep Learning for Diabetic Retinopathy 
Gulshan et al. (2016) trained a deep CNN on a large collection of graded fundus 
photographs and reported high sensitivity and specificity for detecting referable 
diabetic retinopathy. Ting et al. (2017) extended the idea to multiethnic populations and 
to r elated eye diseases such as glaucoma and age -related macular degeneration, 
showing that a single approach can generalise across different groups. Gargeya and 
--- PAGE 22 ---
10 
 
Leng (2017) described a data -driven method for automated identification of DR from 
retinal photographs. Abràmoff et al. (2018) went further and evaluated an autonomous 
AI diagnostic system in primary-care offices, which illustrates both the promise of the 
technology and the regulatory and clinical validation that real deployment requires. 
These works establish the feasibility of the classification task. They all rely on large, 
centrally collected datasets, which is the assumption that the federated componen t of 
EdgeRetina questions. 
2.3.2 Federated Learning in Healthcare 
McMahan et al. (2017) introduced Federated Averaging, in which clients perform 
several local training steps and the server averages the resulting models weighted by 
client data size. Kairouz et al. (2021) and Li et al. (2020) survey the open problems, 
including communication cost, statistical heterogeneity between clients and system 
constraints. In medicine, Rieke et al. (2020) set out the opportunities and the practical 
hurdles of federated digital health, and Sheller et al. (2020) demonstrated multi -
institutional model training for brain tumour segmentation without sharing patient data. 
Applications to retinal imaging are more recent. Raj et al. (2024) built a federated 
EfficientNetB0 system for five-level DR grading across several hospitals and aimed it 
at low-resource clinics. Bhulakshmi and Rajput (2024) proposed FedDL, which applies 
federated averaging across simulated clients with different CNN architectures on public 
fundus datasets. These studies show that federated training is a realistic way to use  
distributed retinal data. EdgeRetina follows the same family of approaches but 
concentrates on a compact, runnable prototype in which the privacy -inspired update 
processing and the explanation are visible in the interface. 
2.3.3 Differential Privacy and Privacy-Aware Federated Learning 
Differential privacy gives a mathematical definition of what it means for the output of 
an algorithm to reveal little about any single individual (Dwork & Roth, 2014). Abadi 
et al. (2016) showed how to train deep networks with differential privacy by clipp ing 
per-example gradients, adding Gaussian noise and tracking the cumulative privacy loss 
with a moments accountant. Geyer et al. (2017) applied the same ideas at the client 
level in federated learning, and Malekzadeh et al. (2021) combined federated learning, 
differentially private training and secure aggregation on a diabetic retinopathy task. Zhu 
et al. (2019) demonstrated that shared gradients can be inverted to reconstruct training 
images, which explains why sharing updates instead of data is not by it self sufficient. 
--- PAGE 23 ---
11 
 
The common thread is that clipping bounds the influence of any one participant and 
noise masks what remains, but a formal guarantee also needs a privacy accountant and 
an analysis of the exact mechanism. EdgeRetina implements the first two ingredients 
and openly omits the third. 
2.3.4 Explainability and Efficient Architectures 
Selvaraju et al. (2017) proposed Grad -CAM, which weights the feature maps of a 
convolutional layer by the gradient of a class score and produces a heatmap over the 
input. Adebayo et al. (2018) warn that saliency methods must be sanity-checked, which 
supports the cautious interpretation adopted in this report. On the architecture side, 
MobileNetV3 (Howard et al., 2019) uses a hardware -aware search and efficient 
building blocks to give a small and fast network, whereas EfficientNet (Tan & Le, 
2019) scales dep th, width and resolution together with a compound coefficient. Both 
are available as pretrained models in Keras (Chollet, 2015), which makes them natural 
candidates for transfer learning on a modest retinal dataset. 
2.4 Findings from the Literature Survey 
The survey leads to four findings. First, deep learning is an effective approach to 
automated retinal image analysis, but the strongest results rely on large centralised 
datasets. Second, federated learning is a credible way to use data held by several 
institutions, and FedAvg is the standard baseline. Third, update sharing leaks 
information, so privacy -oriented processing is advisable, but formal privacy requires 
accounting, and privacy mechanisms trade utility for protection. Fourth, Grad -CAM 
makes CNN pr edictions easier to inspect while remaining a coarse and non -clinical 
visual aid. 
2.5 Research Gap and Positioning of EdgeRetina 
DR classification, federated learning, privacy -oriented processing and explainability 
are often studied separately or in pairs. A student -scale, fully runnable system that 
brings all four together, exposes them through a usable web interface and reports it s 
own limits honestly is less common. EdgeRetina fills this gap as a prototype. It does 
not claim to beat published accuracy figures, to protect privacy formally, or to be 
validated for clinical use. Its contribution is the integration and the transparent 
evaluation workflow.

4.1 Design Approach and Methodology 
EdgeRetina is designed as a layered, modular application. The layers separate what the 
user sees, what the server does, which models are used, where files and results are kept, 
and where predictions are stored. This separation makes it possible to change t he 
interface without touching the models, and to replace a model without changing the 
routes. The design follows an object-oriented decomposition into services and classes, 
documented with UML use-case and class diagrams as required by the review format. 
4.1.1 Overall System Architecture 
Fig. 4.1 shows the architecture of the system. The topmost layer is the web interface 
built with Flask templates, HTML, CSS and JavaScript. It contains the dashboard and 
overview page, the image upload and prediction page, and the prediction-history page. 
Requests from the interface are passed to the Flask backend, which contains three 
groups of functionality: image validation and preprocessing, the prediction service for 
the supported models, and the training service that trains models and saves their 
metrics. The backend calls the deep learning models, MobileNetV3Small and 
EfficientNetB0, both configured for five -class classification. Below the models is the 
dataset and model management layer, which holds the APTOS 2019 dataset and its 
train, validation an d test splits, the training results (model checkpoints in the .keras 
format, training history, metrics and the ensemble status file), and the preprocessed 
images used for training and inference. The SQLite database stores prediction records 
and model infor mation. The whole application runs in the local environment, on a 
Windows machine in the development setup.

4.5 Data Flow and Interaction Between Components 
Two data flows dominate the system. In the prediction flow  the browser posts an 
uploaded image to the prediction route of the Flask backend. The backend passes it to 
the image processor for validation and preprocessing, asks the model loader for the 
selected trained model, and passes the preprocessed array to the prediction service. The 
service returns the class probabilities, from which the predicted class and confidence 
are derived. If the user requests the explanation, the Grad-CAM service reuses the same 
model and image to compute the heatmap. The database service then writes the record, 
and the route returns the result to the page, which renders the class, the confidence, the 
probability bars and the overlay. 
In the training flow  the browser asks the training route to start a run. The 
backend validates the dataset, prepares the preprocessed images, trains the selected 
architectures in two stages, evaluates them on the test split and writes the checkpoints 
and metrics into the mode l management layer. While the run is in progress the page 
polls the backend for status, which is why the interface can show a progress bar and a 
live log. When the run has finished, the prediction page reads the saved metrics to state 
which model is the best verified model. 
In the federated flow the training route creates four client objects, each holding 
one partition of the training data, and a server object holding the global model. For each 
round the server distributes the model, every client trains and produces an update, the 
privacy process or clips and perturbs the update, and the aggregator combines the 
processed updates. Only updates cross the boundary between a client and the server in 
this flow; the image partitions stay inside the client objects.

4.6 Security and Privacy Considerations in the Design 
The design takes a small number of deliberate precautions. Uploaded files are validated 
before they reach the model, which limits the effect of malformed input. The interface 
and the backend never present unverified numbers as results: the prediction page quotes 
only metrics that were produced by the evaluation step. The data of the simulated clients 
are kept in separate partitions and are not mixed during local training. Update clipping 
bounds the influence of each client, and Gaussian noise perturbs what leaves the client. 
These measures improve the posture of the prototype, but they are not a security 
certification. In particular, the application runs locally without authentication, the 
uploaded images are stored on the local machine, and the privacy processing carries no 
formal guarantee, as discussed in Chapter 6. 
4.7 Detailed Description of the Main Classes 
This section describes the responsibility of each class of Fig. 4.4 in more detail. 
ImageProcessor. It is the only place where raw images are handled. 
validate_image checks that a file exists, can be decoded and has a supported format.

runs the two training stages, predict returns the class probabilities for a batch, and 
evaluate computes the test metrics. The common interface makes it easy to compare the 
architectures or to add a third one. 
PredictionService. It coordinates a single prediction. preprocess_input calls the 
image processor, predict_class runs the model, calculate_confidence takes the largest 
probability, and get_probabilities returns all five. It also calls the Grad -CAM service 
and the database service so that the route handler stays short.

5.5 Model Architectures 
5.5.1 Transfer Learning 
Both architectures are used through transfer learning. A backbone pretrained on a large 
image collection supplies general visual features such as edges, textures and shapes. A 
new classification head with five softmax outputs is attached. Training takes pl ace in 
two stages, labelled "head" and "fine_tune" in the training log: first only the new head 
is trained while the backbone is kept fixed, and then the backbone is fine-tuned so that 
its features adapt to retinal images. This is the usual way of obtaining good results from 
a small dataset (Yosinski et al., 2014). 
5.5.2 MobileNetV3Small 
MobileNetV3Small (Howard et al., 2019) is a lightweight CNN designed for efficient 
computation. It combines inverted residual blocks with squeeze -and-excitation 
modules and uses the hard -swish activation, and its architecture was refined by 

--- PAGE 42 ---
30 
 
hardware-aware neural architecture search. It has few parameters, so it trains quickly 
and needs little memory, which makes it suitable where computing resources are 
limited, for example on edge devices. In EdgeRetina it is adapted to five -class 
classification by replacing the original output layer. 
5.5.3 EfficientNetB0 
EfficientNetB0 (Tan & Le, 2019) is the baseline network of the EfficientNet family. Its 
design uses a compound scaling rule that increases depth, width and input resolution 
together in a balanced way rather than scaling a single dimension. It is somewhat 
heavier than MobileNetV3Small but is known for a strong accuracy -to-size ratio. It is 
used here as the second architecture, so that the effect of model capacity on the DR task 
can be compared.

5.8 Handling Class Imbalance 
Because the five classes differ so much in size, the choice of training strategy and of 
evaluation metric matters as much as the choice of architecture. Several standard 
remedies exist. Class weighting  multiplies the loss of each sample by a weight 
inversely related to the frequency of its class, so that errors on rare classes cost more. 
Focal loss (Lin et al., 2017) down-weights the loss of easy, well-classified examples so 
that training concentrates on hard ones, which are often from the minority classes. 
Balanced sampling  draws minority -class images more often in each epoch, and 
targeted augmentation (rotations, flips, brightness changes) creates additional variety 
for the rare grades. The dashboard of the application states that the imbalance of the 
data motivated weighted and focal-loss experiments, which shows that the problem was 
recognised during development. 
The results reported in Chapter 9 show that the imbalance is still visible in the 
final models, since the recall of Mild and Severe DR remains very low. For this reason 
the project reports macro -F1 and the confusion matrix beside the accuracy. A model 
that predicted only the majority class would already obtain an accuracy of about 49% 
on this dataset (1,805 of 3,662 images), and the accuracies of 63.3% and 71.1% have 
to be judged against this reference level, not against 20%, the chance level for five 
balanced classes.

6.1 Motivation for Federated Learning 
In the centralised baseline, all images are in one place. That is convenient for training, 
but in real healthcare it would mean that every hospital exports patient images. 
Federated learning inverts the arrangement: the model travels to the data instead of the 
data travelling to the model. Each hospital keeps its images, trains the shared model 
locally and returns only the result of that training. The server never needs to see an 
image. This is the reason why federated learning is attractive for medical ima ging 
(Rieke et al., 2020; Sheller et al., 2020) and why EdgeRetina includes a simulation of 
it. 
6.2 Simulated Federated Architecture 
The federated component of EdgeRetina has four simulated clients, Hospital A, B, C 
and D, and one federated server. The clients are software objects, each owning a 
partition of the training data. The server holds the global model. Fig. 6.1 summarises 
one round. The server distributes the current global model; every client trains it on its 
own partition; every client then clips and perturbs its update; and the server aggregates 
the processed updates with FedAvg to produce the next global model. The training page 
of the application runs this cycle for a configurable number of aggregation rounds, 
whose default is five, with the explanation that five rounds give a useful learning trend.

6.5 Privacy-Inspired Update Processing 
Sending an update instead of an image is an improvement, but an update is not harmless. 
A large update from a client with a rare image can reveal a lot about that image, and 
gradient-inversion attacks have reconstructed training images from shared gradient s 
(Zhu et al., 2019). EdgeRetina therefore processes every update in two steps before it 
leaves the client: it limits the size of the update by clipping, and it hides fine detail in 
what remains by adding random noise. The training page describes the resul t as 
experimental differential privacy, states that it clips the updates and adds configurable 
Gaussian noise, and states that it does not claim a formal privacy budget.

6.5.4 Limitations of the Privacy Mechanism 
Clipping and Gaussian noise do not automatically make a training procedure 
differentially private. A formal guarantee needs a precisely defined mechanism, a noise 
scale calibrated to the sensitivity that the clipping creates, and an accountant that tracks 
the cumulative privacy loss across rounds to give a pair (ε, δ) (Dwork & Roth, 2014; 
Abadi et al., 2016). EdgeRetina has no accountant and no verified analysis. It therefore 
reports no privacy budget and makes no differential-privacy claim. Secure aggregation, 
homomorphic encryption and encrypted model exchange are not implemented either, 
so the server sees every processed client update in the clear. The mechanism should be 
understood as a demonstration of the standard ingredients, which is what the 
experimental label in the interface says. Its effect on model utility has also not been 
separately measured.

from pathlib import Path 
 
import numpy as np 
import pandas as pd 
 
def dirichlet_partition(frame: pd.DataFrame, clients: list[str], alpha: float = 2.0, 
seed: int = 42) -> dict[str, pd.DataFrame]: 
    rng = np.random.default_rng(seed) 
    assignments = {client: [] for client in clients} 
    for label in sorted(frame["diagnosis"].unique()): 
        indices = frame.index[frame["diagnosis"] == label].to_numpy() 
        rng.shuffle(indices) 
        proportions = rng.dirichlet(np.full(len(clients), alpha)) 
        boundaries = (np.cumsum(proportions) * len(indices)).astype(int)[:-1] 
        for client, values in zip(clients, np.split(indices, boundaries)): 
            assignments[client].extend(values.tolist()) 
    return {client: frame.loc[sorted(indices)].reset_index(drop=True) for client, 
indices in assignments.items()}

def fedavg(weight_sets: list[list[np.ndarray]], sample_counts: list[int]) -> 
list[np.ndarray]: 
    if not weight_sets or len(weight_sets) != len(sample_counts) or

9.8 Discussion 
Four conclusions follow from the results. First, EfficientNetB0 is the better model by 
accuracy and is the model that the application names as the best verified model, which 
is consistent with its higher capacity. Second, overall accuracy hides the real behaviour: 
--- PAGE 72 ---
60 
 
both macro-F1 values are around 41–42%, far below the accuracies, because the Mild 
and Severe grades are almost never recognised correctly. Third, the imbalance of the 
dataset, with 1,805 No DR images against 193 Severe ones, is the most likely cause, 
because a model that predicts the majority class often is rewarded by accuracy. The 
weighted and focal -loss experiments mentioned in the dashboard are the natural 
remedies. Fourth, the errors are mostly between neighbouring grades, as the kappa and 
MAE values show, so the model captures the ordinal structure of the disease even when 
it does not name the exact grade. The system is thus useful as a research prototype and 
as a demonstration of the workflow, but its performance on the minority grades is not 
sufficient for any clinical purpose. 
9.9 Error Pattern Analysis 
The confusion matrix of EfficientNetB0 allows the main error patterns to be identified. 
Of the 56 Mild images, 36 (64%) are predicted as Moderate, so Mild DR is mostly 
absorbed by the neighbouring class. Of the 29 Severe images, 15 (52%) are predicted 
as Proliferative and 12 (41%) as Moderate, so the Severe class is split between its two 
neighbours. Of the 44 Proliferative images, 23 (52%) are predicted as Moderate. 
Among the 150 Moderate images, 105 are correct, while 24 are predicted as No DR 
and 20 as Pr oliferative. In almost all cases the predicted grade is adjacent to or two 
grades away from the true grade, and only a handful of images are confused across the 
whole range, such as a few No DR images that are called Proliferative. This pattern is 
the reason for the comparatively high kappa value and the low MAE. 
For comparison, the per -class values of the centralized baseline run, derived 
from its confusion matrix in the same way, are given in Table 9.6. The baseline 
recognises Mild DR better than the later model (recall 33.9% against 3.6%), but it is far 
weaker on No DR (recall 73.4% against 97.4%) and on Moderate DR (29.3% against 
70.0%), and it never predicts Severe DR correctly. The improvement in overall 
accuracy of the later models therefore comes mainly from the two large classes, and in 
the case of EfficientNetB0 it is paid for with a lower recall on the Mild class. This is a 
typical effect of class imbalance: as the model becomes more confident on the frequent 
classes, the rare classes are predicted less often.

9.10 Threats to Validity 
Several factors limit how far the results can be generalised. The test set contains only 
550 images and the minority classes are small (29 Severe and 44 Proliferative images), 
so the per-class values, particularly the recall of the Severe class, are based on very few 
images and carry considerable statistical uncertainty. A single train, validation and test 
split was used, so the variability across different splits and random seeds has not been 
measured. The images come from one public dataset and one challenge, so the reported 
performance may not transfer to other cameras or populations. The labels were assigned 
by human graders and contain some noise, which affects the ceiling of achievable 
accuracy, in particular between neighbouring grades. Finally, the f ederated results are 
missing, so no statement about the cost of federation or of the privacy -inspired 
processing in terms of accuracy can be made. These threats do not invalidate the 
workflow demonstrated by the project, but they have to be kept in mind wh en 
interpreting the numbers.

10.3 Ethical and Regulatory Considerations 
Any system that handles medical images must respect the privacy of patients and the 
rules that govern medical software. The APTOS 2019 images are distributed for 
research under the terms of the public challenge, and EdgeRetina uses them for 
academic purposes only. The prototype stores uploaded images and predictions locally, 
and anyone who wanted to use it with real patient images would need informed consent, 
an ethics approval, secure storage and a data -protection assessment. Diagnostic 
software that influ ences clinical decisions is regulated as a medical device in most 
countries and needs clinical validation, which EdgeRetina has not undergone. The 
interface and this report therefore state clearly that the output is a research result and 
not a diagnosis. 
Fairness is a second concern. A model trained on one dataset can perform 
differently for patients with different ethnicity, age, camera type or image quality, and 
the low recall on rare grades means that the model could systematically under-report .

CHAPTER 11 
SUMMARY 
EdgeRetina is a research prototype for privacy-aware diabetic retinopathy classification 
that combines deep learning, simulated federated learning, privacy -inspired update 
processing and explainable artificial intelligence in a single software system. It uses the 
APTOS 2019 Blindness Detection dataset of 3,662 retinal fundus images and classifies 
them into five severity categories: No DR, Mild, Moderate, Severe and Proliferative 
DR. 
Two architectures, MobileNetV3Small and EfficientNetB0, were implemented 
through transfer learning and evaluated on a common test set of 550 images. 
EfficientNetB0 reached a test accuracy of 71.1% with a macro -F1 of 40.9%, and 
MobileNetV3Small reached 63.3% with a macro -F1 of 42.0%. The confusion -matrix 
analysis of EfficientNetB0 showed that the model is strong on No DR and Moderate 
DR but recognises the Mild and Severe grades poorly, an effect of the strong class 
imbalance. The results are centralised results. 
A federated learning environment with four simulated hospital clients was 
implemented. The clients train locally, their updates are clipped to a norm of 1.0 and 
perturbed with Gaussian noise, and the server aggregates them with Federated 
Averaging over a c onfigurable number of rounds. This is a privacy -inspired 
mechanism. No privacy accountant is implemented, so no formal differential -privacy 
guarantee is claimed, and no secure aggregation or encryption is used. Test results for 
the federated global model were not recorded and are not reported. 
Grad-CAM was integrated to provide heatmap explanations, and a Flask web 
application allows users to upload an image, obtain the predicted class, the confidence 
and the class probabilities, view a Grad -CAM overlay, run training and consult a 
prediction his tory stored in SQLite. Twelve functional test cases were recorded as 
passed.The recommendations that follow from the work are to evaluate the federated 
model on the same test set, to tackle the class imbalance with weighted or focal losses 
and balanced sampling, to add privacy accounting, to validate the explanations against 
clinical annotations, and to test on external and heterogeneous data. With these 
extensions EdgeRetina can grow from a demonstration of the workflow into a basis for 
a more rigorous study of privacy-preserving and explainable retinal screening.

def update_status(status: str, message: str, progress: int, current_model: str | None = 
None, metrics=None): 
    if not args.status_file: 
        return 
    args.status_file.parent.mkdir(parents=True, exist_ok=True) 
    payload = {"status": status, "message": message, "progress": progress, 
"current_model": current_model, "metrics": metrics, "output": "", "pid": 
os.getpid()} 
    args.status_file.write_text(json.dumps(payload, indent=2), encoding="utf-8") 
 
metrics = {} 
try: 
    for index, (architecture, loss) in enumerate((("MobileNetV3Small", 
"weighted_crossentropy"), ("EfficientNetB0", "focal"))): 
        name = architecture.lower() 
        progress = 5 if index == 0 else 55 
        update_status("running", f"Training {architecture}. This may take several 
minutes.", progress, architecture, metrics) 
        print(f"Training {architecture}...", flush=True) 
        metrics[architecture] = train_centralized(root / "data" / "splits", 
Config.IMAGE_DIR, output / f"{name}.keras", output / f"{name}.json", root / 
"reports" / "experiments" / f"{name}.json", args.epochs, args.batch_size, True, loss, 
architecture, "macro_f1", root / "reports" / "experiments" / f"{name}_history.json") 
    update_status("completed", "Verified multi-model ensemble is ready.", 100, 
"Complete", metrics) 
except BaseException as exc: 
    update_status("failed", str(exc), 0, None, metrics) 
    raise
